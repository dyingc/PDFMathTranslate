# PDF 翻译小应用（DeepSeek）

在 pdf2zh 之上加一层极简 Web UI：上传 PDF → 选语言/模型 → 下载译文。公式、图表版式由 pdf2zh 的
版面模型保留，本应用不碰这部分逻辑。

## 特性

- 后端模型：`deepseek-v4-flash` / `deepseek-v4-pro`（DeepSeek OpenAI 兼容接口）
- API Key **只存在服务端进程内存**中：
  - 保存时会先调一次 DeepSeek `/models` 做校验
  - 浏览器只拿到一个 `sid` 会话 cookie（httponly），刷新页面无需重新输入
  - 应用重启 → 内存清空 → 需重新输入
  - 已禁用 pdf2zh 的配置落盘（见 `app.py` 顶部对 `ConfigManager._save_config` 的处理），
    否则 pdf2zh 会把 `DEEPSEEK_API_KEY` 写进 `~/.config/PDFMathTranslate/config.json`
- 界面支持全部 10 种语言（与可翻译的目标语言相同），在首屏即可切换，
  选择存服务端 `data/settings.json`，首次使用默认简体中文
- 可选思考强度（`off` / `low` / `high` / `max`，对应 DeepSeek 的 `thinking` 与
  `reasoning_effort`），默认 `high` 与 API 默认行为一致
- 每个任务显示实际 token 用量与费用（人民币），按**每次调用当时的价格**累计
- 输出可选：纯译文（`-mono.pdf`）、原文/译文对照（`-dual.pdf`）或两者
- 除 API Key 外的设置都是持久的：并发参数存服务端 `data/settings.json`，
  界面上的语言/模型/输出等选择存浏览器 localStorage
- 中断或失败的任务可以一键「继续」（复用 pdf2zh 的段落缓存，已翻部分不再花钱）
- 任务记录存 SQLite、产物存固定目录，刷新页面或重启应用都不会丢；任务列表从服务端记录渲染，
  因此翻译大文件时可以随意刷新/关标签页

## 运行

```bash
./webapp/start.sh          # 默认 8077
./webapp/start.sh 8123     # 指定端口
```

端口被本应用的旧实例占用时会先杀掉旧的、沿用同一端口；被其他程序占用则自动在
8000-9000 里找一个空闲端口。也可以直接跑 `.venv/bin/uvicorn webapp.app:app --port 8077`。

### 并发

两个并发参数在**页面顶部直接可调**（与界面语言并列），改完立即生效并写入
`data/settings.json`：

- **同时翻译的文件数**（1-16）：调大立刻放行正在排队的任务；调小不会打断
  正在跑的，只是不再启动新的
- **每个文件的 LLM 线程数**（1-32）：对新开始的任务生效

也可以在启动时指定，作为首次运行的初始值：

```bash
./webapp/start.sh -w 4 -t 8
```

等价环境变量 `WEBAPP_WORKERS` / `WEBAPP_LLM_THREADS`。优先级是
环境变量 > 上次保存的值 > 默认值（2 / 4）。

打给 DeepSeek 的并发请求上限是两者相乘，调大前先确认账号的速率限制；
版面分析是 CPU 密集的，任务并发过高会互相抢核。

打开 http://127.0.0.1:8077 ，填入 DeepSeek API Key（https://platform.deepseek.com/api_keys）即可。

首次启动会下载版面分析模型和目标语言字体，需要等待一会儿。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/config` | 可选模型、语言，以及当前会话是否已有 key |
| POST | `/api/session` | 表单 `api_key`，校验后写入内存并下发 cookie |
| DELETE | `/api/session` | 清除本会话的 key |
| POST | `/api/translate` | 表单 `file`/`model`/`lang_in`/`lang_out`/`pages`/`output`，返回 `job_id` |
| GET | `/api/jobs` | 全部任务记录（倒序，最多 50 条） |
| GET | `/api/jobs/{id}` | 轮询进度；完成后 `kinds` 列出可下载的类型 |
| POST | `/api/jobs/{id}/resume` | 重跑中断/失败的任务 |
| DELETE | `/api/jobs/{id}` | 删除记录与文件（进行中的任务拒绝删除） |
| GET | `/api/jobs/{id}/download/{mono\|dual}` | 下载结果 |

## 翻译上下文

pdf2zh 原本是**一段一次请求**：没有标题、没有相邻段落、没有术语表。在本应用自己的缓存上
统计（4000 条样本），送出的单元中位数 147 字符，而 **17% 短于 40 字符**——章节标题、
编号，甚至出现过孤零零的一个字母 `n`。模型拿到这些只能猜，而且每次猜得不一样，
于是术语在全文范围内漂移。

障碍是结构性的：pdf2zh 在版面循环内部逐段请求翻译，手上永远没有下一段。所以这件事
挪到那个循环**之前**做（`webapp/context.py`）：

1. **采集**：把 translator 切到回显模式（`DEEPSEEK_COLLECT`），完整跑一遍版面，
   不花一分钱，拿到的正是 pdf2zh 稍后会逐段请求的那些段落，且按阅读顺序
   （该遍固定 `thread=1`，否则并发会打乱顺序）；
2. **描述**：从**全文均匀采样**（不是只看开头，核心术语常首次出现在中段）问一次，
   得到标题 / 领域 / 一句话摘要；
3. **成块翻译**：按 ~2000 字符组块，段落不拆开，用 JSON 收发；
4. **回填缓存**：逐段写进 pdf2zh 的缓存，正式那一遍全部命中，不再调用 API。

### 为什么用带 id 的 JSON

裸数组的错位是**静默**的：模型合并了两段，后面所有译文整体错一格，落到错误的版面区域上——
这比翻译质量差严重得多。带 id 后校验的是「id 集合完全一致」，不一致就整块丢弃。
丢弃是安全的：没写进缓存的段落，正式那一遍会按老办法逐段翻译。这套机制**只影响质量，
不影响正确性**，任何一步失败都能优雅退化。

### 提示词的顺序不是随意的

DeepSeek 按**前缀**计价缓存，只从第一个 token 开始逐字匹配。所以固定部分（规则 + 文档描述）
必须在最前，逐块变化的正文在最后。写反了，整个任务的缓存命中率归零，输入 token 从
¥0.02/M 变成 ¥1/M。

顺序对了还不够：第一块**单独发**，发完再并发其余的。实测一个 33 次调用的任务直接并发时，
输入 token 只有 23% 命中前缀缓存——第一波并发请求全都在前缀被记住之前就发出去了。
这不是浪费一次探测调用，第一块是真活，只是不并发而已。

### 文档描述按"提取所用文本"记住

描述一份文档要花一次调用，而它给出的 `field` 是缓存键的一部分——不记住的话，
重跑时连"这些段落是不是已经缓存过"都得先花钱问一遍文档是什么。所以描述结果存在
`data/profiles/` 下。

键不是文件名，也不是文件哈希，而是**送去提取的那段采样文本的 sha256**。
文件名会撞（不同内容都叫 `SPA.pdf`）也会变；文件哈希则把排版元数据、生成器版本、
书签这些与提取毫无关系的东西也算了进去——PDF 重新保存一遍就白重跑一次。
按采样文本作键，不变量才对齐：**同样的输入喂给同样的提取，结果必然一样**。
代价为零，因为采集那一遍免费且本来就跑在描述之前。

附带的正确行为：只翻两页和翻全书会得到不同的采样、不同的键。全书样本推断出的描述
本来就更好，不该被两页的结果顶掉。

实测：同一文件跑两次，第二次 **0 次调用**；把 PDF 重新保存一遍（每个字节都变了、
标题和 producer 也改了），仍然 **0 次调用**。
将来的术语表存进同一个文件、同一把键，不需要第二套机制。

### 术语表

**不译词表就是术语表**，不需要第二套机制：一条译法等于原词的条目（`NSA -> NSA`）
本身就是"保持原样"。

术语从两处来：

1. **文档描述那一次调用顺带返回**最多 25 条核心术语——不额外花钱，而且赶在任何
   翻译之前，所以并发的头几块一开始就有共识；
2. **每块翻译顺带返回**它用到、但表里还没有的新术语——同样不额外花钱。

发请求前扫一遍本块正文，只把**出现在这一块里的**术语注入（上限 40 条，长的优先）。
全量注入会把真正的任务挤到提示词后面，且每次调用都要付这笔 token。

变体（`sound` / `unsound` / `soundness`）**由模型在首次调用时一并给出**，不在代码里
推导。后缀规则只对英文成立，而 `lang_in` 是可配置的；何况它照样处理不了
`analysis/analyses`、`index/indices` 这类不规则变化，而技术文档恰恰重度依赖这些词。

代码里只保留一条**排版**归一化：连字符和空格互换。71% 的术语是多词，而英文同一个复合词
在名词位用空格、在定语位用连字符（`context sensitivity` / `context-sensitive`）。
这是排版不是形态，用拉丁字母的语言都一样，所以值得写死。

这些都是在 SPA.pdf 上付了代价才定下来的：

- 抽取给出的是词条式写法 `Fixed point`，正文写的是 `fixed point`，精确匹配导致
  议定的「不动点」**一次都没被注入**，译文用了「定点」20 次；
- 更糟的是词形。`Soundness` 被钉成「可靠性」，而形容词 `sound` 是**另一个字符串**、
  术语表管不着，模型自由发挥成了「健全」。该词一致率从**没有术语表时的 83% 掉到
  有术语表时的 64%**——**术语表自己把文档劈成了两半**。

### 首次调用给多少料

关键判断是：**输入几乎免费，输出才是成本**。20k 字符的摘录约 ¥0.01，而术语条数直接决定
输出长度，且那张表之后每一块都要带着走。所以摘录给得大方，术语数给得克制：

```
摘录  = clamp(3000, 正文字符数 / 20, 20000)
术语数 = clamp(25,   正文字符数 / 4000, 80)
```

实测：NSA（48 页 / 58k 字符）→ 摘录 3000、25 条；SPA（207 页 / 348k 字符）→ 摘录 17402、80 条。

但摘录再大也只是文档的一部分，**模型没见过的术语就钉不住**。所以除了摘录，还送一份
**全文词频表**（前 120 个高频词 + 前 60 个高频二元组，附出现次数）。它扫的是全部正文、
计算不花钱、排序依据恰好就是"这个词重不重要"。约 3000 字符，比摘录还便宜。

变体也是从这里来的。SPA 的词频表里并排躺着：

```
sound (85)      soundness (48)
fixed (58)      fixed-point (64)     fixed point (47)
analysis (833)  analyses (56)
```

`sound` 比 `soundness` 还频繁——这正是只钉住名词伤害那么大的原因。模型把它们并排看到，
自己就能判断是一组。

注入位置是**用户消息里、正文之前**，不是固定前缀——术语表在任务过程中一直在长，
放进前缀会让整个任务的前缀缓存全部失效。

### 先到先得，以及并发留下的尾巴

同一术语的多个译法，**先写入的永久胜出**。一致性本身就是目的，全文统一地用一个
次优译名，好过局部最优、全局漂移。

但并发意味着头几块彼此看不见对方的术语，可能各自造出不同译法。胜出者从此被使用，
可那几块**自己的译文里已经写了落败的译法**。所以全部完成后做一次改写：
把落败译法替换成胜出译法。

护栏是**包含关系**：`切片 -> 程序切片` 作用在已经写了"程序切片"的文本上会得到
"程序程序切片"。两个译法互为子串时跳过替换。

改写是**对着缓存做**的，不是在写缓存之前：块一完成就立即入缓存，崩溃不会丢掉
已经付过钱的工作；缓存条目冲突即替换，所以把改好的文本再写一次就够了。

实测（构造的冲突：第一块造"稀疏"、其余三块造"疏松"）：1 条冲突译法在 11 个段落里
被改写，缓存里最终只剩"稀疏"，正式那一遍 0 次未命中。

术语表随文档描述一起存进 `data/profiles/`，所以同一文档的后续运行**开局术语就已
议定**，不必重新发现。

### field 进缓存键，title 和 summary 不进

译文是在文档描述的影响下产生的，所以一条缓存只在那个描述仍然成立的地方才可复用。
`field` 是其中粗到值得共享的部分：两篇机器学习论文可以互换译文，一份法律合同和一篇
物理论文不行。`title` 和 `summary` 每份文档都不同，进了键就等于每个文件独占一套缓存，
和没有缓存一样。

顺带说明跨文档复用到底值多少：缓存里有 8259 条，而一篇没翻过的新论文命中 **0 条**。
要命中得两篇文档有逐字相同的长段落，现实中只发生在同一篇论文的不同版本或版权样板上。
缓存真正在赚钱的是**同一份文件的重复跑**——resume、换输出版本重跑。

### 缓存键会被上下文加宽

段落级缓存能跨文档复用，这是想要的——但只对**足够长**的段落成立。
`2.1 Overview` 或 `In this section we describe our approach.` 的译法取决于后文，
拿它当键几乎能命中世界上任何一篇文档。所以短于 200 字符的段落，键是**它自己加上后续段落**，
拼到 200 字符为止；查和写用的是同一个键映射，两遍因此一致。

拿不到键映射时（关掉了上下文、或段落没被采集到），短段落**不读也不写缓存**——
宁可多花一次调用，也不把一个没有上下文的译法散播到别的文档里。

### 不值得翻译的段落

去掉占位符后短于 3 个字符、或不含任何字母的段落（页码、`1.`、`{v3}`）直接原样返回，
不调用 API 也不写缓存——这是一条规则，不是一个结果。`'n'` 曾经就是这样被翻成了
「TIP 的 n。」。

### 代价

多一遍版面 pass（纯 CPU，不调用 API），大约让整体耗时增加两三成。
设 `WEBAPP_CONTEXT=0` 可退回 pdf2zh 原本的逐段行为。

## 扫描件

上传时会检测扫描件（页面几乎全是图片、但能提取出文字 = 有 OCR 层）。命中时**先弹窗询问**，
不会先花钱翻完再让你发现结果没法看。

原因：扫描件里你看到的原文是**图片里的像素**，pdf2zh 只能删除文字绘制指令，删不掉像素，
所以译文会直接叠在原文的照片上。

确认继续后，翻译完成会自动做一次清理：用源文件自身的**段落边界框**定位原文位置，
擦除该区域扫描图上的像素（`apply_redactions(images=PIXELS, text=NONE)`），译文、图表、
线条都保留。代价是这些区域里的底纹或背景也会被一并擦掉。

用段落框而不是逐个文字 span，是因为 OCR 层的 span 并不铺满段落，逐 span 擦会在行间
留下一条条没擦干净的原文碎片——这一点在 weiser 那份 OCR 质量较差的扫描件上很明显。

## 代码块

pdf2zh 会把代码块当成普通段落：合并成一段、送去翻译、再按行宽重排，换行、缩进和
等宽字体全部丢失。用回显翻译器（不调用 API）也能复现，可见破坏来自版面重排本身，
与模型无关。

修法是给 `translate()` 传 `vfont`——匹配到的字体会被原样保留、不参与翻译与重排。
`webapp/app.py` 里的 `VFONT` 在 pdf2zh 内置的公式字体规则之外，补上了等宽字体族
（`txtt`、`cmtt`、Courier、Consolas、Menlo、Inconsolata 等）。

**注意 `vfont` 一旦传入就会覆盖内置规则**，所以 `VFONT` 必须是内置规则的超集，
否则公式会被当成正文翻译掉。冒烟测试会从 pdf2zh 源码里抽出内置规则逐条比对。

代价：代码里的注释不再被翻译。用排版正确、注释是英文的代码，换排版稀烂、注释是
中文的代码，这个交换是划算的。

`VFONT` 里还包含 `CMR[567]`——5-7pt 的 Computer Modern Roman 只会是上下标，
不会是正文。留作正文的后果是：一个上下标就把整块逐字保留的内容（文法、公式）
变成"文字+公式"的混合段落，pdf2zh 随即按**段落字号**（那个极小的上标字号）
重排行距，行间距从 12pt 塌缩到 3.8pt，两行直接叠在一起。CMR8 以上可能是真正的
脚注正文，仍然参与翻译。

## 代码块的位置

`vfont` 让代码块的**内容**逐字保留，但它的**位置**仍受段落排版摆布：版面模型经常
把「正文 + 代码块 + 正文 + 代码块」识别成一个区域，而 pdf2zh 的段落就是区域，
于是代码块被内联进流式段落，压在正文上。

版面模型只看得见图像，但 PDF 自己知道等宽文本在哪。`webapp/verbatim.py` 把这些
矩形补进模型的输出，标成 `isolate_formula`——`translate_patch` 会把这类区域涂成
「保留区」。代码块因此各自成段、按原坐标锚定，周围的正文也在正确的位置断开。

两条防误伤的规则：**至少两行**（句子里的单个等宽词不算块），且**该纵向区间内不能
有正文行**（否则会把一个段落拦腰截断）。

依赖一个上游约定：`translate_patch` 对每页恰好调用一次 `model.predict`，且按页序
调用——我们靠调用序号把页面对上预先算好的矩形。冒烟测试会检查这个约定。

## 一行被切成三段

pdf2zh 给每个版面区域一个段落号，再按字符所在区域分配段落。**一个只盖住某行中段、
没盖到两端的区域，会把这一行切成三个段落**，而且经常断在词中间。SPA.pdf 第 22 页：

```
[0] 'More ex'
[1] 'ample programs can be found in the Scala implementatio'
[2] 'n of TIP.'
```

肇事者是一个 conf 0.47 的多余 `plain text` 区域（x 195–442），切点正好是 195 和 442。
这一行本身不在任何其他区域内，所以左右两截落在默认区域、中间一截属于那个框，
扫描时 `1 → i+2 → 1` 就成了三段。

修法是**把切了某一行的区域横向撑开到完整覆盖那一行**（`verbatim.heal_cuts`）。
选撑开而不是丢弃，是因为模型对这个区域的判断可能有对的部分——它的垂直范围不动，
只沿 x 生长，且只长到它本来就压着的那些行。双栏排版天然安全：没有一行横跨两栏，
所以一个区域最多长到本栏宽度。

效果（SPA.pdf 全书，用回显翻译器统计，不花钱）：段落数 1532 → 1515，
在词中间断开的相邻段落 132 → 117，TIP 那句恢复完整。

残留的两类修不掉，也不该在这里修：**跨页续段**（pdf2zh 逐页翻译）和
**区域在竖直方向从段落中间断开**——后者要合并上下相邻区域，很容易把两个
真正不同的段落并成一个，风险大于收益。

## 目录页

目录页会被**跳过、保留原文**。pdf2zh 的排版单位是版面模型识别出的区域，
整块目录就是一个区域：条目被合并成一个段落再按宽度折行，"1.1 静态程序分析的应用
............11.2 近似答案" 就是这么来的。

真正的修法是把版面图按行拆分，那在 `high_level.translate_patch` 内部，
要复制上百行函数体。跳过只要十几行：该页原样透传，对齐、点线、页码全部保持，
而页码本来就不需要翻译。与代码块是同一笔交易——**能用的英文 > 错乱的中文**。

识别依据是"一行里有 4 个以上点线引导符"，且整页出现 4 行以上。
实测 6 份文档：SPA 的 3 页目录全部命中，其余文档零误报（最多 2 行）。
若整份文档都被判定为目录，则不跳过。

## 超链接

pdf2zh 的 mono 输出保留了全部链接，但 dual 的组装走 PyMuPDF `insert_file`，
它搬不动**命名目标**（named destination）——LaTeX 的交叉引用和目录项全是这种。
这本 624 条链接里有 618 条就此消失。

翻译完成后会重建：命名目标解析成显式的页面目标（不再依赖名称表），
并把页号映射到译文页，点进去仍然是中文。

**不能沿用原坐标**——译文重排后 "Chapter 12"、"[LSS+15]" 早已不在原处。
每条链接按**锚文本**重新定位：先整段搜索，失败则退回锚文本里的记号
（章节号、引用键、数字）——恰好这些都是翻译不会改动的部分。
找不到就丢弃：**放错位置的链接比没有链接更糟**。

同时从原注释复制 `/Border` 与 `/C`——hyperref 画的彩色方框来自这两个键，
新建的链接默认带 `/BS <</W 0>>`（零宽边框），能点但完全看不见。
注意 `page.get_links()` 在页面重载前看不到刚插入的注释，取 xref 要用 `annot_xrefs()`。

mono 页面上原有的链接会先删除再重建，因为它们停留在原坐标、早已对不上译文。
dual 的英文页不属于处理范围，链接原样保留。

## 图内标签重影

有些插图是「画两遍、后一遍盖前一遍」导出的：第一遍的标签在原文里被后画的不透明色块
完全盖住，读者只看到第二遍。pdf2zh 重建页面时把**所有文字排在所有图形之后**
（`pdfinterp.py`：`q {ops_base}Q ... {ops_new}`，为的是不让译文被图片埋掉），
于是那层本该看不见的标签浮到了最上面，和可见标签错位重叠。

翻译完成后会自动做一次去重，只删除**能被证明在原文里不可见**的文字：
被后画的不透明填充框完整覆盖的 span。两条保险：

- 只有当该位置**还有别的字符存活**时才删——两遍往往是插图的不同修订版
  （本例里是 COND / PRED），存活者不必与它相同；若删完会留下空洞，宁可保留重影
- 删除按区域生效，会连同存活的那份一起抹掉，因此删除前先记录、删除后原样重画

对没有隐藏层的文档，这一步是空操作。

## 费用计算

`pricing.json` 是价格表，单位为元 / 百万 tokens，取自[官方中文定价页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)（不是汇率换算）。
它按生效时间分档，每档可带峰谷时段：

- 2026-08-17 00:00（北京时间）前：统一定价
- 之后：高峰时段为北京时间 9:00-12:00、14:00-18:00，空闲时段价格减半

费用**不是**任务结束后用总 token 数乘以当前价格算的，而是**每次 API 调用返回时**
按那一刻生效的价格立即累加。这样跨越峰谷分界、甚至跨越调价时点的长任务也算得对，
和 DeepSeek 自己的计费方式一致。缓存命中的 token 单独计价（便宜得多），
取自响应里的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`。

官方调价时，在 `regimes` 数组**末尾追加**一条即可，不要修改历史条目——
旧任务的费用是按它当时的价格算出来存下的，改动历史条目会篡改已有账目。

## 数据存放

默认在 `webapp/data/`（已 gitignore），可用环境变量 `PDF2ZH_WEBAPP_DATA` 覆盖：

```
data/
  jobs.sqlite          # 任务记录
  settings.json        # 并发、界面语言等设置（不含 API Key）
  jobs.sqlite          # 含每个任务的 token 用量与费用
  files/<job_id>/      # <名字>-mono.pdf / <名字>-dual.pdf
```

上传的原件在翻译成功后删除（可重新上传），译文一直保留，直到你在界面上点"删除"。
应用重启时，处于 queued/running 的任务会被标记为 `interrupted`——进程内的翻译线程无法跨重启恢复。
这类任务（以及失败的任务）保留着上传的原件，可以在界面上点「继续」重跑。

「继续」不是字节级续传（pdf2zh 没有这个概念），而是用相同参数重跑一遍。
pdf2zh 按段落文本哈希缓存译文，已经翻好的段落直接命中缓存，不会重复调用 API，
所以实际只为未完成的部分付费。费用是**累加**到原有记录上的，不会覆盖。
